# Интерактивная установка на Ubuntu Server

Поддерживаемые установщиком версии: Ubuntu Server 22.04 и 24.04.
Используйте отдельную чистую копию исходников на сервере, без локальных `.env`,
`.secrets`, `node_modules` и результатов сборки. Нужны Python 3, sudo/root,
домен с DNS на этот сервер, открытые TCP 80/443 и внешний HTTPS-приемник аудита.
Ориентир ресурсов: 4 vCPU, 8 ГБ RAM, 60 ГБ SSD; это не гарантия пропускной способности.

Из корня проекта:

```sh
sudo python3 scripts/install-production.py
```

Установщик запрашивает домен, администратора, продукт, offline-режим, приемник
аудита, его токен (скрытый ввод) и каталог будущих резервных копий.
При отсутствии Docker предлагает установку из его официального apt-репозитория.
Метод установки: https://docs.docker.com/engine/install/ubuntu/.
Существующие конфликтующие контейнерные пакеты автоматически не удаляются.
При уже установленном Docker требуется работающий Compose plugin.

Затем создаются свежие секреты, Ed25519-пары и манифест с production issuer;
собираются контейнеры, применяются миграции и runtime-права, запускаются сервисы.
После успешной HTTPS readiness-проверки создаются администратор и продукт.
Внешний приемник должен принимать JSON POST и устранять дубли по Idempotency-Key.
Наличие URL не доказывает доставку: получение событий нужно проверить отдельно.

## Результат

- `INSTALLATION_RESULT.txt` — адрес сайта и следующие действия.
- `.secrets/install-admin.json` — пароль и bootstrap для WebAuthn; чтение root.
- `.secrets/client-config.json` — публичная конфигурация для release-сборки клиента.
- `.env` и `.secrets/keystore.json` — production-конфигурация и онлайн-ключи.
- `.secrets/manifest-root.pem` — корневой приватный ключ, который после защищенного
  резервирования необходимо перенести в офлайн-хранилище оператора.

```sh
sudo cat .secrets/install-admin.json
```

Завершите регистрацию WebAuthn через сайт в течение 15 минут. Сохраните пароль
в менеджере паролей и удалите файл начальных учетных данных. Не присылайте его
содержимое в переписку. Ключи сервера не передавайте на машину сборки desktop:
достаточно публичного `client-config.json`.

## Повторный запуск

Повторите ту же команду. Установщик хранит настройки и не заменяет существующие
секреты, пароли, продукт или базу. Миграции и выдача прав выполняются повторно.
До удаления файла начальных учетных данных повторный запуск обновляет срок
bootstrap; после удаления не создает его заново и не сбрасывает пароль.
Два установщика одновременно не запускаются благодаря файловой блокировке.
Не изменяйте домен или идентичность продукта через внутренний файл настроек:
смена домена требует отдельной процедуры WebAuthn/issuer и переподписи манифеста.

Установщик отказывается перезаписывать `.env`, созданный не им. Автоматического
импорта локальной разработки нет. При сбое создания материалов до записи
настроек установщик восстановит исходные ответы; issuer не изменяется.
Перед повторной попыткой после ошибок диска проверьте целостность файлов.

## Что остается оператору

DNS, внешний firewall, аренда сервера и создание приемника аудита выполняются
оператором. Скрипт не меняет SSH/firewall, не регистрирует домены, не отправляет
секреты внешним службам. Сертификат HTTPS получает Caddy.

Каталог резервных копий создается, но расписание, шифрование, вынос копий на
другой сервер и пробное восстановление НЕ настраиваются автоматически.
Настройте их по `DEPLOYMENT.md` до допуска реальных пользователей.
После переноса в рабочие файлы временные дубликаты секретов удаляются.
При аварийном завершении каталог `.secrets/installer` может содержать остатки:
учитывайте их при защищенном резервировании и переносе корневого ключа.

Обновление приложения, восстановление базы и ротация ключей — отдельные
операторские процедуры. Не используйте установщик как автоматический откат.
Не запускайте `docker compose down -v` на рабочей системе.

Установщик не заменяет нагрузочное тестирование и проверку безопасности.
Полный сетевой запуск нужно проверить на целевом Ubuntu-сервере с реальным DNS.
