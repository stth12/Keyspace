ТРЕБОВАНИЯ К РАЗВЕРТЫВАНИЮ СИСТЕМЫ KEYSPACE / ONLINEKEYGEN
Дата: 19.09.2026

Документ относится к текущему проекту и docker-compose.production.yml.
Дополнение: теперь доступен интерактивный установщик для Ubuntu 22.04/24.04:
  sudo python3 scripts/install-production.py
Запускать из отдельной чистой production-копии. Полная инструкция:
docs/runbooks/INSTALLER_RU.md. Ручной порядок ниже остается альтернативой.
Описывает подготовку самостоятельного сервера. Локальный запуск на компьютере
не означает, что система уже опубликована в интернете.

1. ЧТО НЕОБХОДИМО ПОДГОТОВИТЬ

Обязательно:
- Сервер с Linux, постоянным IP-адресом и административным доступом.
- Docker Engine и Docker Compose v2 с поддержкой используемого compose-файла.
- Домен и доступ к управлению DNS.
- Исходный код проекта, включая package-lock.json, Prisma migrations,
  Dockerfile, docker-compose.production.yml и конфигурацию Caddy.
- Отдельные production-пароли, криптографические ключи и файл .env.
- Внешний приемник событий аудита, доступный по HTTPS.
- Отдельное защищенное место для резервных копий.
- Администратор системы и средство WebAuthn для его второго фактора.

Для первоначального планирования небольшой установки можно заложить
4 vCPU, 8 ГБ RAM и 60 ГБ SSD. Это оценка для планирования, а не результат
нагрузочного теста. Сборка Docker-образов, рост базы, журналов и резервных копий
требуют дополнительного места. Перед реальной нагрузкой нужны измерения.

На сервере не требуется отдельно устанавливать Node.js, PostgreSQL, Redis
или Rust, если сборка и запуск выполняются через Docker.
Для операторских скриптов вне Docker требуется Node.js 24 и npm.

2. КАКИЕ КОМПОНЕНТЫ БУДУТ ЗАПУЩЕНЫ

frontend       — сайт и пользовательский/административный интерфейс Next.js.
backend        — NestJS API, пользователи, лицензии, сессии и проверки доступа.
postgres       — PostgreSQL 17, основная база данных.
redis          — Redis 7, ограничения частоты запросов и временные данные.
worker         — доставка событий аудита во внешний приемник.
reverse-proxy  — Caddy, HTTPS и маршрутизация запросов.
migrate        — разовый служебный контейнер миграций и подготовки базы.

Браузер и desktop-клиент обращаются к общему HTTPS-адресу.
Маршруты /api/ обслуживает backend, остальные — frontend.
PostgreSQL и Redis доступны только внутри серверной сети Docker.

Текущая конфигурация рассчитана на один сервер. Автоматическое переключение
на резервный сервер, кластер базы и балансировка нескольких серверов
не предоставляются этим Compose-файлом.

3. ДОМЕН, СЕТЬ И HTTPS

- Создать DNS A-запись домена на IP сервера. AAAA добавлять только при наличии
  работающего IPv6-маршрута к этому серверу.
- Разрешить входящие TCP 80 и 443. UDP 443 нужен только для HTTP/3.
- Ограничить административный доступ к серверу доверенными адресами/VPN.
- Не публиковать наружу PostgreSQL, Redis, порт API 4000 и frontend 3000.
- Обеспечить исходящий доступ для скачивания образов, получения сертификатов
  Caddy и отправки аудита.
- Настроить синхронизацию времени сервера.

Caddy получает TLS-сертификат автоматически при корректном DNS и доступности
домена. Его постоянные тома необходимо сохранять при обновлениях.

4. НАСТРОЙКА ОКРУЖЕНИЯ

Основа списка параметров: .env.example. Реальные значения нельзя помещать
в Git, клиентское приложение, публичные документы или журналы.

DOMAIN                      — домен без https:// и без пути.
WEB_ORIGIN                  — https://ВАШ_ДОМЕН.
API_ISSUER                  — тот же HTTPS-адрес, совпадающий с manifest issuer.
RP_ID                       — домен без схемы; используется WebAuthn.
NODE_ENV                    — production.
POSTGRES_PASSWORD           — пароль владельца/мигратора базы.
RUNTIME_DB_PASSWORD         — отдельный пароль ограниченной роли приложения.
REDIS_PASSWORD              — отдельный пароль Redis.
DATABASE_URL                — подключение ограниченной роли приложения.
MIGRATION_DATABASE_URL      — подключение роли для миграций и provisioning.
REDIS_URL                   — подключение к Redis с паролем.
KEYSTORE_FILE               — путь к серверному .secrets/keystore.json.
JWT_ACCESS_SECRET           — отдельный случайный секрет веб-токенов.
LICENSE_HMAC_SECRET         — отдельный секрет HMAC лицензионных ключей.
LICENSE_HMAC_ACTIVE_KEY_ID  — идентификатор действующего HMAC-ключа.
LICENSE_HMAC_PREVIOUS_JSON  — предыдущие HMAC-ключи; изначально {}.
OBSERVABILITY_SECRET        — секрет для защитных идентификаторов событий.
CHACHA_MASTER_KEY           — ключ криптографической подсистемы шифрования.
AUDIT_SINK_URL              — HTTPS-адрес внешнего приемника аудита.
AUDIT_SINK_TOKEN            — токен доступа к приемнику, если требуется.
MANIFEST_ROOT_PRIVATE_KEY_FILE — путь к корневому ключу на машине оператора.

Симметричные криптографические секреты: независимо сгенерированные CSPRNG
32 байта, представленные 64 строчными шестнадцатеричными символами.
Нельзя использовать одинаковое значение для разных назначений.

Production Compose формирует часть адресов и URL самостоятельно из DOMAIN,
паролей и внутренних имен сервисов. Имена postgres и redis доступны внутри
Docker-сети; они обычно не разрешаются на машине оператора вне этой сети.
Для операторских команд нужен отдельный корректный контекст подключения.

5. КЛЮЧИ ПОДПИСИ И ПЕРВОНАЧАЛЬНАЯ ПОДГОТОВКА

Необходимо подготовить свежий .secrets/keystore.json установленного проектом
формата: отдельные Ed25519-ключи для application-session и offline-license,
идентификаторы, сроки действия, статусы, публичный корневой ключ и подписанный
манифест публичных ключей для production API_ISSUER.

Корневой приватный ключ подписи манифеста хранить отдельно у оператора.
В обычный backend-контейнер он не передается. В desktop включается только
корневой публичный ключ.

Production-подготовку теперь выполняет интерактивный установщик, вызывающий
scripts/setup-production.ts. Команда npm run setup:dev
создает локальную конфигурацию с localhost и не является готовой настройкой
публичного сервера. Нельзя переносить действующие локальные учетные данные
и секреты в production.

Формат начального хранилища описан реализацией scripts/setup-dev.ts.
Если этот генератор используется как техническая основа в новом изолированном
окружении, все созданные материалы должны быть свежими, настройки необходимо
заменить на production, а манифест переподписать для нужного issuer.
Одна только замена API_ISSUER в .env недостаточна.

После применения миграций и provisioning оператор может переподписать
манифест командой:
  npx tsx scripts/rotate-keys.ts manifest

Команда требует доступа к базе через MIGRATION_DATABASE_URL, корневому
приватному ключу и записи в каталог keystore. Она выполняется до открытия
доступа пользователям. Стандартный migrate-контейнер монтирует .secrets
только для чтения, поэтому без отдельной операторской конфигурации эта
команда в нем не сработает.

Права файлов должны разрешать чтение keystore пользователю backend-контейнера
(USER node), но не посторонним пользователям. Проверить владельца, группу
и права прохода по каталогам. Не делать секреты общедоступными ради запуска.

6. ПОРЯДОК РАЗВЕРТЫВАНИЯ

Все команды ниже запускаются из корня проекта. До начала должны быть готовы
.env, свежие секреты, первоначальный keystore и адрес приемника аудита.
Никаких реальных паролей в этом документе нет.

Шаг 1. Собрать образы, включая служебный профиль:
  docker compose -f docker-compose.production.yml --profile ops build

Шаг 2. Поднять базу и Redis:
  docker compose -f docker-compose.production.yml up -d --wait postgres redis

Параметр --wait не заменяет проверку готовности Redis: в текущем Compose
для него не задан healthcheck. Проверить доступность перед следующими шагами.

Шаг 3. Применить миграции:
  docker compose -f docker-compose.production.yml --profile ops run --rm migrate

Шаг 4. Создать ограниченную runtime-роль, выдать права и зарегистрировать ключи:
  docker compose -f docker-compose.production.yml --profile ops run --rm migrate npx tsx scripts/provision.ts

Шаг 5. Проверить соответствие подписанного манифеста production API_ISSUER.
Если он был создан для localhost, выполнить описанное выше переподписание
из защищенного операторского окружения. Проверить сроки действия ключей.

Шаг 6. Запустить остальные сервисы:
  docker compose -f docker-compose.production.yml up -d backend frontend worker reverse-proxy

Шаг 7. Проверить состояние:
  docker compose -f docker-compose.production.yml ps

Проверить по HTTPS:
  https://ВАШ_ДОМЕН/api/v1/health/live
  https://ВАШ_ДОМЕН/api/v1/health/ready

Затем открыть сайт, проверить регистрацию, авторизацию и работу администратора.
Статическая спецификация API: docs/api/openapi.json.
Интерактивный Swagger включается в development, а не в production.

7. ПЕРВЫЙ АДМИНИСТРАТОР И ПРОДУКТ

В защищенном операторском окружении с Node.js 24:
  npm ci
  npm run db:generate
  npm run admin -- create administrator
  npm run admin -- product keyspace "Keyspace" --offline

Флаг --offline добавлять, только если этому продукту нужен автономный режим.
Команды должны использовать production-базу, Redis и корректный keystore.
Доступ организуется через защищенное подключение либо операторский контейнер
внутри сети; публично открывать базу для этого не нужно.

Создание администратора записывает начальные учетные данные и bootstrap-токен
в .secrets/admin-bootstrap.json. На подключение WebAuthn отводится 15 минут.
После сохранения пароля в защищенном менеджере и настройки MFA удалить файл
с начальными учетными данными. Не отправлять его в переписку и не коммитить.

При необходимости оператор может выдать новый bootstrap:
  npm run admin -- mfa-bootstrap administrator

Эти команды записывают файлы в .secrets. Стандартный read-only mount сервиса
migrate не подходит для них без специально подготовленного окружения.
Создание продукта возвращает UUID; он нужен для конфигурации desktop-клиента.

8. ПОДГОТОВКА DESKTOP-КЛИЕНТА

Сервер и установщик приложения развертываются отдельно.
Для новой серверной установки необходимо обновить публичный файл:
  apps/desktop/src-tauri/client-config.json

Поля:
- api_url — HTTPS-адрес production API;
- issuer — точное значение production API_ISSUER;
- product_id — UUID продукта из production-базы;
- root_public_key — публичный корневой ключ проверки манифеста.

Существует scripts/desktop-config.ts для генерации конфигурации из операторского
окружения. На сборочную машину достаточно передать публичную конфигурацию;
приватные серверные ключи там не нужны.

Для сборки Windows-клиента нужны Windows, Node.js 24, Rust/Cargo, инструменты
сборки Microsoft C++ и Windows SDK. На целевом компьютере нужен WebView2.
После подготовки зависимостей и публичной конфигурации:
  npm run tauri -w @lk/desktop -- build

Для распространения подготовить release-сборку, подписать установщик
сертификатом подписи кода организации и проверить на чистой Windows.
Имеющийся локальный debug-установщик с localhost не является production-релизом.

9. АУДИТ, РЕЗЕРВНОЕ КОПИРОВАНИЕ И ЭКСПЛУАТАЦИЯ

Приемник аудита предоставляется отдельно: в Compose готового внешнего
хранилища аудита нет. Он должен принимать JSON POST по HTTPS, при необходимости
проверять Bearer-токен, возвращать 2xx и исключать дубли по Idempotency-Key.
Нужны неизменяемое хранение и контроль доступа. Worker повторяет неудачные
доставки; следует контролировать накопление недоставленных событий.

Настроить:
- Резервные копии PostgreSQL и, при необходимости малого окна потери данных,
  архивирование WAL. Срок хранения и допустимую потерю данных задать отдельно.
- Отдельное защищенное резервирование keystore, HMAC-секретов и корневого ключа.
- Шифрование резервных копий отдельным ключом и хранение вне основного сервера.
- Регулярное пробное восстановление в новую изолированную базу.
- Мониторинг доступности API, диска, памяти, ошибок, Redis и очереди аудита.
- Ограничение размера контейнерных журналов и исключение секретов из логов.
- Обновление зависимостей, проверку уязвимостей и фиксацию проверенных образов.
- Ротацию ключей до истечения сроков ключей и манифеста.

Файловое хранилище ключей требует перезапуска API после ротации.
После изменения переменных окружения контейнеры нужно пересоздать:
обычный docker compose restart новые значения .env не подхватывает.
Старые HMAC-секреты нельзя просто удалять: для оставшихся лицензий требуется
миграция при предъявлении ключа либо контролируемый отзыв и перевыпуск.

Сохранять постоянные тома postgres-data, redis-data, caddy-data и caddy-config.
Не выполнять docker compose down -v на рабочей установке: это удаляет тома.

10. ПРОВЕРКИ ПЕРЕД ДОПУСКОМ ПОЛЬЗОВАТЕЛЕЙ

[ ] DNS и HTTPS работают, доступ к базе и Redis из интернета закрыт.
[ ] Production-секреты отличаются от локальных; в клиенте нет private keys.
[ ] Миграции применены, права runtime-роли ограничены.
[ ] Манифест, issuer, product_id и публичный ключ клиента согласованы.
[ ] WebAuthn администратора настроен на реальном домене.
[ ] Регистрация, вход, refresh и выход проверены.
[ ] Выпуск и первая активация лицензии работают.
[ ] Заблокированная, отозванная и истекшая лицензии не проходят проверку.
[ ] Чужой продукт и превышение лимита устройств отклоняются.
[ ] USER не получает доступ к административным действиям.
[ ] Ограничения частоты запросов и доставка аудита проверены.
[ ] Offline-токен имеет ограниченный срок даже для Lifetime.
[ ] Резервная копия восстановлена в отдельном окружении.
[ ] Пройдены тесты проекта, проверены зависимости и release-установщик.
[ ] Проведены нагрузочная проверка и независимая проверка безопасности
    в объеме, соответствующем назначению публичной системы.

Offline-проверка не обеспечивает мгновенный отзыв на отключенном устройстве.
Модифицированное приложение может обходить собственные локальные ограничения;
доступ к серверным функциям всегда должен проверяться сервером.

11. ЧТО ПРЕДСТОИТ ПРЕДОСТАВИТЬ ДЛЯ РЕАЛЬНОГО ЗАПУСКА

1) Сервер, его адрес и защищенный административный доступ.
2) Домен и возможность изменить DNS.
3) Адрес/доступ к внешнему приемнику аудита.
4) Место хранения резервных копий и правила их хранения.
5) Ответственного администратора и средство WebAuthn.
6) Название продукта и решение, разрешать ли offline-режим.
7) Сертификат подписи кода для распространяемого Windows-установщика.
8) Отдельно подготовленные production-секреты и ключи.

Само создание этого документа не меняет конфигурацию и не публикует систему.
Дополнительные инструкции: docs/runbooks/DEPLOYMENT.md, .env.example,
docker-compose.production.yml, scripts/provision.ts, scripts/rotate-keys.ts.
